# Business Entity Resolution — Approach

Amazon ML Challenge 2026 · 25–27 Sep 2026 · metric **F₀.₅ macro-averaged per Source-1 entity**

---

## 1. Confirmed data facts

Measured directly from the training files, not assumed.

| | Train | Test |
|---|---|---|
| Source 1 (reference) | 2,206,821 | 1,732,544 |
| Source 2 | 5,034,616 | 4,887,273 |
| Source 3 | 5,285,603 | 5,082,316 |

**Countries.** Train: US 1.32M / India 0.88M. Test: India 0.81M / US 0.66M / **France 0.26M (15% of test S1, entirely unseen)**.

**Ground-truth distribution.** Mean 3.46 matches per S1 entity (S2: 1.67, S3: 1.79). Mode is 3. Range 0–11.
Singletons are only **5.6%** — so the all-empty baseline scores just **0.056**. There is no cheap floor here.

Singleton rate is 5.588% for India and 5.583% for US — identical to three decimal places. Combined with the uniform match-count distribution, this says the data is **synthetically generated by the same corruption process per country**. That is very good news for France: the noise model should be identical, only the language differs. A language-agnostic pipeline transfers; a country-conditioned one does not.

### Three structural properties that shape everything

**(a) The matching is many-to-one — confirmed exactly.**
7,638,365 matched-ID occurrences, 7,638,365 unique IDs, **zero reuse**. Every S2/S3 record belongs to at most one S1 entity. This is not a soft tendency; it is exact in the training data. It licenses a global assignment constraint (§6.2) that most teams will not exploit.

**(b) Matches never cross country — confirmed.**
0 cross-country pairs in 734,066 checked. Blocking within country is free recall-wise and cuts the search space by ~3×. It also means France can be processed as a completely independent shard.

**(c) 73–74% of S2/S3 records match some S1.** So roughly a quarter of S2/S3 are distractors with no S1 home.

## 2. The metric, derived

The official definition simplifies. With `k` = number of predicted IDs, `T` = true set, `TP` = correct predictions:

```
P = TP/k,  R = TP/|T|
F₀.₅ = 1.25·P·R / (0.25·P + R)
     = 1.25·TP / (0.25·|T| + k)        ← use this form
```

Verified against the statement's worked example: TP=2, k=3, |T|=2 → 1.25·2/(0.25·2+3) = 2.5/3.5 = **0.7143** ✓ (they quote 0.714).

Conventions: k=0 and |T|=0 → 1.0. k=0 and |T|>0 → 0. k>0 and |T|=0 → 0.

### What this implies — read this twice

For an entity with 3 true matches:

| Prediction | F₀.₅ |
|---|---|
| all 3 correct | **1.000** |
| 2 correct, miss 1 | **0.909** |
| all 3 correct + 1 false positive | **0.789** |
| 2 correct + 1 false positive | 0.714 |

**Dropping an uncertain candidate costs less than including a wrong one.** Missing a true match costs ~0.09; adding a false positive costs ~0.21 — more than twice as much. Every threshold decision must be biased toward precision.

Because it is macro-averaged, an entity with 1 match counts exactly as much as one with 11. Do not optimise anything pair-weighted; optimise the per-entity mean.

## 3. What the noise actually looks like

Real examples from train:

```
S1  Raj Investments LLP        | 6(29), C.I.T. Colony, 2Nd Main Road Mylapore, Chennai, Tamil Nadu
S2  ராஜ் இன்வெஸ்ட்மெண்ட்ஸ் எல்எல்பி    | 6(29), C.I.T. COLONY, 2ND MAIN ROAD MYLAPORE, CHENNAI, Tamil Nadu
S3  Raj Investments எல்எல்பி     | 6(29), C.i.t. Colony, 2Nd Main Road Mylapore, Chennai, TN
S3  ராஜ் இன்வெஸ்ட்மெண்ட்ஸ் எல்எல்பி    | 6(29), C.i.t. Colony, ... , Chennai, தமிழ்நாடு

S1  Payne Enterprises          | 3315 Fremont Street, Peoria, IL
S2  Payne Énterprises          | 3315 FREMONT ST, PEORIA, IL
S2  Payne Enterpires           | 3315 FREMONT ST, PEORIA, IL
S2  PAYNE-ENRTPRMISES          | 3315 FREMONT SAINT, PEORIA, IL
S3  Payne Etrepndiels          | 3315 Fremont St, Peoria, Illinois
S3  Payne Enterprises  LLC     | Fremont St, Peoria, Illinois
```

Observed corruptions: full transliteration into Tamil/Devanagari script, partial transliteration (suffix only), accent injection (`Énterprises`), character-level typos (`Etrepndiels`), adversarial abbreviation expansion (`St` → `SAINT`), state abbreviation both ways (`IL`↔`Illinois`, `Tamil Nadu`↔`TN`↔`தமிழ்நாடு`), legal-suffix addition/removal, punctuation, case, and dropped address components (house number gone in the last row).

### The two conclusions that matter

**Address is a far stronger signal than name.** Names get destroyed — a Tamil-script name shares *zero* character n-grams with its Latin original. Addresses keep the street number and street token nearly intact across every variant. Also: **13.6% of S1 business names are exact duplicates of another S1 name**, so name alone cannot identify an entity even when clean.

→ **Block primarily on address. Use name as a scoring feature, not the primary blocking key.** A name-first blocker silently loses every transliterated record, and that is a large slice of the India shard.

**Transliteration needs explicit handling.** Two cheap, high-value tools:
- `unidecode` romanises Tamil/Devanagari phonetically (`ராஜ்` → `raj`), after which ordinary character similarity works. Pure-Python, no external data, no licence issue.
- A multilingual sentence encoder (LaBSE — Apache-2.0, or `multilingual-e5-base` — MIT) embeds the Tamil and Latin forms near each other. Both well under 8B.

Most teams will do neither and will cap out on the India shard.

## 4. Pipeline

```
normalise → block (per country) → pair features → model → calibrate
          → assignment constraint → per-entity k selection → output
```

### 4.1 Normalisation

One function, applied identically to all sources and all countries. No country conditioning.

- Unicode NFKD, strip combining marks (`Énterprises` → `Enterprises`)
- `unidecode` for non-Latin scripts; **keep both raw and romanised forms** as separate fields
- lowercase, collapse whitespace, strip punctuation (keep digits)
- legal-suffix canonicalisation: `corp|corporation`, `pvt|private`, `ltd|limited`, `inc|incorporated`, `llp`, `llc`, `co`, and the French set `sarl|sas|sa|eurl|snc` — include France's suffixes even though they are not in train; that is general knowledge encoded in code, not an external lookup
- street-type canonicalisation: `rd|road`, `st|street|saint`, `ave|avenue`, `blvd|boulevard`, `ln|lane`, `nagar`, `marg`, and French `rue|av|bd|place`
- US state abbreviation ↔ full name table, Indian state ↔ abbreviation, both directions
- extract structured sub-fields: leading house number, all digit runs, postal/PIN code (5–6 digits)

### 4.2 Blocking — this sets your recall ceiling

Run **per country**, union of several complementary blockers. Target ≥98% recall with ≤50 candidates per S1.

1. **Numeric address key** — house number + first alphabetic street token, e.g. `3315|fremont`, `6(29)|cit`. Extremely high precision, survives transliteration because digits are script-invariant. This is the workhorse.
2. **Address char-TF-IDF cosine**, char_wb 3–5 grams, top-K by sparse matmul per country shard.
3. **Name char-TF-IDF cosine** on the *romanised* name — catches records with damaged addresses.
4. **Multilingual embedding ANN** on `name + address`, top-K via FAISS/HNSW. This is the recall safety net for the cases the lexical blockers miss.
5. **Rare-token inverted index** — index on IDF-weighted rare tokens from either field.

Measure and report: **blocking recall** (fraction of true pairs present in candidates) and **reduction ratio**. Blocking recall is a hard ceiling on the final score — check it before training anything. `candidate_pairs.tsv` is a required deliverable and is exactly this stage's output.

### 4.3 Pair features

Computed for each (S1, S2/S3) candidate. Vectorise; there will be tens of millions of pairs.

**Name similarity** (on both raw and romanised forms): Jaro-Winkler, normalised Levenshtein, token-sort ratio, token-set ratio, token Jaccard, char-3gram Jaccard, TF-IDF cosine, IDF-weighted token overlap, longest common substring ratio.

**Address similarity**: the same set, plus — exact house-number match (binary, very strong), digit-sequence Jaccard, postal-code match, street-token overlap after canonicalisation, count of shared rare address tokens.

**Cross-field**: name tokens appearing in the other record's address and vice versa (catches field-swap noise).

**Script/language**: is either name non-Latin, do the scripts differ, romanisation similarity minus raw similarity.

**Relational features — do not skip these, they are among the strongest.** For each candidate, relative to the other candidates of the same S1 entity: rank by each base similarity, ratio to the best-scoring candidate, margin to the second-best, z-score within the candidate group, number of candidates for this S1. A candidate that is merely *good* matters far less than one that is *clearly the best available*.

**Bidirectional**: is this S1 also the best candidate for this S2/S3 record (mutual nearest neighbour)? Rank of this S1 in the S2/S3 record's own candidate list. This directly encodes the many-to-one structure.

### 4.4 Model

**Primary: LightGBM binary classifier** on the pair features. This is the standard winner for entity resolution and it will carry most of the score. Train on candidate pairs with label = in ground truth. Use `scale_pos_weight` or subsample negatives — the candidate set is heavily imbalanced.

**Secondary: cross-encoder.** Fine-tune a small transformer on `[name1, addr1] [SEP] [name2, addr2]` pair classification. Use a **multilingual** backbone so transliterated pairs are learnable — `multilingual-e5-base` (MIT) or LaBSE (Apache-2.0), both ≪8B and licence-compliant. Do **not** run it over all ~50M pairs; run it only on the uncertain band (GBDT probability in roughly 0.15–0.85) where it changes decisions. That is maybe 10–15% of pairs and makes it affordable.

**Ensemble**: rank-average or logistic stack of GBDT + cross-encoder, fitted on out-of-fold predictions.

Licence check for the final package: DeBERTa-v3 MIT, LaBSE Apache-2.0, multilingual-e5 MIT, sentence-transformers Apache-2.0, LightGBM MIT. All compliant.

## 5. Validation protocol

**Split by S1 entity, never by pair.** Hold out entities and *all* of their candidates, mirroring how the test set works.

**Leave-one-country-out is the France proxy and it is mandatory.** Train on US, validate on India, and vice versa. If the score collapses across that split, the pipeline has learned country-specific patterns and will fail on 15% of the test set. This is the single best instrument you have for the France risk — use it to make design decisions, not just to report a number.

Corollaries: never feed raw `country` as a model feature (use it only for blocking); never one-hot it; never fit country-specific thresholds.

Score with the exact `F₀.₅ = 1.25·TP/(0.25·|T| + k)` macro-average, including singletons. Trust it over the public leaderboard — the private leaderboard decides final rank.

## 6. The decision layer — where the score is won

Most teams will apply a single global probability threshold. That leaves several points on the table.

### 6.1 Per-entity k selection (expected-F₀.₅ maximisation)

Given calibrated probabilities `p₁ ≥ p₂ ≥ … ≥ pₙ` for an entity's candidates, the optimal prediction under independence is a **top-k** rule — so we only need to choose k.

For each k = 0…n compute the expected score

```
E[F₀.₅] = 1.25 · E[ TP / (0.25·|T| + k) ]
```

where TP ~ Poisson-binomial over the selected candidates and `|T|` = TP + Poisson-binomial over the unselected. Compute exactly by DP over the two Poisson-binomial distributions (n is small, ~20–50), or by Monte Carlo if time is short. Pick the argmax k.

This handles singletons automatically: when every `pᵢ` is low, `E[F₀.₅]` for k=0 equals `∏(1−pᵢ)`, the probability the entity really has no matches, and the rule predicts empty on its own.

Calibrate probabilities first — isotonic regression on a held-out fold. **Uncalibrated probabilities make this step actively harmful.**

### 6.2 Global assignment constraint

Because each S2/S3 record belongs to at most one S1 (§1a), any S2/S3 ID claimed by two different S1 entities is wrong at least once. Resolve greedily: sort all (S1, candidate, p) triples by p descending and assign each S2/S3 ID to the first S1 that claims it; drop later claims.

This only ever removes predictions, so it strictly raises precision — which F₀.₅ weights double. Apply it **before** the k-selection in §6.1 so k is chosen over the surviving candidates.

A Hungarian/min-cost-flow formulation is the exact version, but greedy captures nearly all of it at a fraction of the cost. Do not spend Day 3 on the exact solver.

### 6.3 Reverse-direction pass

Reframe as: for each S2/S3 record, which S1 does it belong to (or none)? This is argmax over its own candidate S1 list and enforces many-to-one by construction. Roughly 26% should resolve to "none".

Run it as a second view and use agreement between the two directions as a feature — and, late in the event, as an ensemble. Bidirectional agreement is a strong precision signal.

## 7. Compute plan

The scale is the real adversary: 1.73M test S1 against ~10M S2+S3. At 30 candidates each that is ~52M pairs to featurise and score.

**RAM is the binding constraint, not GPU.** Loading all three test sources as Python strings already exhausts 15.6 GB — we hit a `MemoryError` doing exactly that during EDA. Therefore:

- **Shard by country and process one shard at a time.** France (259k S1) is small enough to use as the fast iteration loop — it is also the shard you understand least, so iterate there.
- Store normalised fields as `category`/`pyarrow` dtypes; never hold raw + normalised + features simultaneously.
- Write candidate pairs and features to Parquet in chunks; stream them into LightGBM rather than materialising one array.
- Use `uint32` IDs internally, mapping back to string IDs only at output time.

**Where to run what:** `ml.g5.xlarge` (24 GB VRAM / 16 GB RAM) once quota clears; the RTX 4060 for blocking and LightGBM (both CPU-bound) in the meantime. The GPU is only needed for the embedding ANN and the cross-encoder.

## 9. Risks

| Risk | Mitigation |
|---|---|
| **France collapse** (15% of test) | Leave-one-country-out validation from hour 12; zero country conditioning anywhere; French suffix/street tables in normalisation |
| **Blocking recall caps the score** | Measure it explicitly per country before modelling; it is a hard ceiling |
| **Transliterated names invisible to lexical blockers** | Address-primary blocking + `unidecode` + multilingual embeddings |
| **RAM exhaustion** | Country sharding, Parquet streaming, integer IDs |
| **Over-predicting** | F₀.₅ punishes FPs ~2.3× more than FNs — bias every threshold toward precision |
| **Public/private leaderboard gap** | Select on leave-one-country-out CV, never on the public board |
| **Submission rejected on format** | Run `utils/validate_submission.py` before every upload |

## 10. What makes this competitive

Five things most of the ~89,000 registrants will not do:

1. **Derive and optimise the actual metric** — `1.25·TP/(0.25|T|+k)`, macro-averaged, with per-entity k chosen by expected-F₀.₅ rather than one global threshold.
2. **Exploit the many-to-one constraint** — verified exactly in the data, and a free precision win under a precision-weighted metric.
3. **Block on address, not name** — the only way to catch transliterated records, which a name-first blocker loses silently.
4. **Handle transliteration explicitly** — `unidecode` plus a multilingual encoder.
5. **Validate leave-one-country-out** — the only honest proxy for the France shard that is 15% of the test set.
